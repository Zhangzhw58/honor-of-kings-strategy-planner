# 王者荣耀局势规划器：项目架构设计

版本：0.1

更新时间：2026-08-18

状态：MVP 基线方案

## 1. 架构目标

本方案面向 Android 实时对局辅助场景，以打野视角为第一优先级，实现“画面采集 → 状态识别 → 局势重建 → 战术决策 → 悬浮提示”的端侧闭环。

架构必须满足以下目标：

- 从画面采集到建议展示的端到端延迟不超过 5 秒，常规目标不超过 2 秒。
- 默认抽帧频率不高于 2 Hz；设备负载较高时允许自动降频。
- 实时数据默认只在设备本地处理，未经用户明确同意不上传原始画面。
- 输出必须包含动作、目标区域、理由、置信度和风险。
- 规则可解释、可测试，模型可独立替换，客户端展示不依赖具体模型实现。
- 不执行触控、按键或游戏进程注入，仅采集用户授权的屏幕内容并展示建议。

## 2. 总体架构决策

MVP 采用“Android 单进程模块化应用 + Python 离线模型工具链”。

- Android 端负责屏幕采集、端侧推理、状态融合、规则决策、悬浮展示和本地诊断。
- Python 工具链负责数据清洗、标注转换、训练、评估、量化和模型导出，不参与实时链路。
- Android MVP 保持单进程，模块之间通过 Kotlin 接口和领域对象通信，不引入 AIDL 或 Messenger。
- 实时链路采用有界缓冲和 `latest-only` 背压策略：推理繁忙时丢弃旧帧，不排队处理已经过时的局面。
- 第一版不依赖云端推理、LLM 文案生成、Drools 或其他重量级规则框架。

```text
┌──────────────────────────── Android 端 ────────────────────────────┐
│ MediaProjection → 帧采样/裁剪 → 视觉识别 → 时序融合 → 规则决策     │
│       │              │            │          │          │          │
│   CaptureFrame   PreparedFrame  Observation  GameState  Decision   │
│                                                                ↓   │
│ 用户反馈 ← 悬浮提示/语音 ← 文案生成 ← 稳定器/节流 ←───────────────┘   │
│    │                本地指标、可选脱敏样本、规则/模型版本             │
└────┼───────────────────────────────────────────────────────────────┘
     ↓ 用户明确授权后导出
┌──────────────────────── Python 离线工具链 ─────────────────────────┐
│ 数据导入 → 标注/校验 → 训练 → 评估 → 量化/导出 → 模型清单生成       │
└───────────────────────────────────────────────────────────────────┘
```

## 4. Android 实时链路

### 4.1 会话与权限

`AnalysisSessionService` 作为前台服务管理一次分析会话：

1. 用户在 Activity 中主动启动分析并授权屏幕捕获。
2. 使用 `MediaProjectionManager` 获取授权结果并创建 `MediaProjection`。
3. 服务创建 `VirtualDisplay` 和 `ImageReader`，通知栏持续显示采集状态。
4. 用户停止、授权被系统撤销或投屏回调触发时，立即释放 `Image`、`VirtualDisplay` 和 `MediaProjection`。
5. 悬浮窗权限与屏幕捕获权限分别处理；拒绝悬浮权限时可降级为应用内预览或通知。

采集服务只持有会话状态和管线入口，不包含识别或决策业务规则。

### 4.2 帧采集与预处理

`ScreenCaptureSource` 输出带单调时钟时间戳的 `CaptureFrame`。采集层遵循以下规则：

- `ImageReader` 缓冲数量保持较小，并通过 `acquireLatestImage()` 获取最新画面。
- 每个 `Image` 必须在 `finally` 中关闭；Bitmap、ByteBuffer 和中间张量尽量池化复用。
- `FrameSampler` 默认每 500～1000 ms 选择一帧，并根据推理耗时、温度和前后台状态调整。
- `FramePreprocessor` 根据屏幕尺寸、方向和 UI 布局配置裁剪 ROI：小地图、计时、状态栏、主视野等。
- 颜色转换、缩放和归一化集中完成，避免每个识别器重复处理整帧。
- 游戏 UI 版本或分辨率无法识别时输出 `UnsupportedLayout`，不得继续生成高置信度建议。

### 4.3 并发与背压

使用 Kotlin Coroutines 和 `Flow` 组织实时管线，但领域接口不依赖 `ViewModel` 或 UI 类型。

- 采集、推理和持久化使用独立受控调度器；主线程只处理 UI 状态和轻量事件。
- 帧流使用容量为 1 的共享通道或等价 `conflate` 策略，保证旧帧不会排队。
- 同一模型解释器默认串行调用，避免线程安全问题和内存峰值；多个独立模型是否并行由真机基准决定。
- 每阶段设定超时并返回可诊断失败，不吞异常、不阻塞后续帧。
- 会话停止时使用结构化并发取消所有子任务，禁止遗留后台推理。

## 5. 状态识别与模型架构

### 5.1 MVP 识别策略

不要用单个大模型直接从完整画面生成战术。MVP 使用“固定 UI ROI + 专用识别器 + 传统视觉规则”的组合：

| 识别任务 | MVP 实现 | 输出 |
| --- | --- | --- |
| 游戏布局 | 分辨率/锚点模板匹配 | `LayoutProfile`、ROI 坐标、可信度 |
| 小地图实体 | 轻量目标检测模型 | 英雄/塔/野怪类别、框、阵营、置信度 |
| 玩家状态 | ROI 分类或规则检测 | 存活、生命区间、回城/交战状态 |
| 游戏时间 | 数字 OCR 或数字分类器 | 秒数、置信度 |
| 技能/资源状态 | 图标分类 + 颜色/模板规则 | 可用性、刷新状态、置信度 |
| 主视野事件 | 后续按数据收益增加检测器 | 团战、塔下风险、可见英雄 |

优先把小地图检测、时间识别和关键资源状态做可靠，因为这些信息对“去哪里”决策的价值最高。装备细节、完整经济 OCR 和复杂主视野理解不进入首个垂直切片。

### 5.2 模型运行时选择

MVP 基线采用 LiteRT，详细决策和数据契约见 `docs/adr/0001-mvp-model-stack.md` 与 `docs/03-模型与数据规范.md`。小地图检测采用 EfficientDet-Lite0 320×320 INT8，游戏时间采用专用数字 CNN；敌方位置首版采用概率状态模型。若基准无法满足要求，更换方案需形成新 ADR。

模型运行时的持续评估依据：

- 目标设备上的 P50/P95 推理时间和峰值内存。
- CPU、GPU、NNAPI delegate 的兼容性与回退行为。
- INT8/FP16 量化后的精度损失。
- APK 增量体积、ABI 覆盖、许可证和维护活跃度。
- Python 训练框架到端侧格式的导出稳定性。

### 5.3 统一模型接口

每个模型适配器实现与具体运行时无关的领域接口：

```kotlin
interface PerceptionModel<I, O> {
    val metadata: ModelMetadata
    suspend fun infer(input: I): InferenceResult<O>
    fun close()
}
```

`ModelMetadata` 至少记录：

- `modelId`、语义版本、文件 SHA-256。
- 输入尺寸、颜色空间、归一化方式。
- 标签表版本、量化类型、运行时版本。
- 训练数据版本、评估指标和最低支持应用版本。

所有模型资产通过 `model-manifest.json` 注册。加载时验证清单、哈希和契约版本；失败时禁用对应能力并降级，不使用不匹配的标签表继续推理。

### 5.4 后处理与可信度

- 模型输出先经过阈值过滤、NMS、坐标映射和阵营校验，再形成 `Observation`。
- 原始模型分数不得直接等同于业务置信度；应使用验证集做校准并记录版本。
- 每个观测包含来源模型、帧时间戳、置信度和 ROI 坐标系。
- 低于最低阈值的结果表达为未知，不用默认值补齐。

## 6. 局势重建

单帧识别结果不直接进入决策器。`GameStateReconstructor` 维护一个有限时间窗口，将多个 `ObservationBatch` 融合为稳定的 `GameState`。

核心职责：

- 将小地图像素坐标转换为统一的归一化地图坐标和 `MapRegion`。
- 使用短时跟踪抑制检测抖动，合并同一英雄的连续观测。
- 为不可见敌方保留 `lastSeenAt`、最后区域和候选区域概率，并随时间衰减置信度。
- 根据游戏时间、塔/资源状态和可见事件推导阶段、目标窗口与风险区域。
- 为每个字段保留新鲜度；字段过期时转换为未知，禁止无限沿用旧状态。

建议的核心契约：

```kotlin
data class GameState(
    val schemaVersion: Int,
    val capturedAtElapsedMs: Long,
    val gameTimeSec: Int?,
    val phase: GamePhase,
    val self: PlayerState,
    val allies: List<HeroState>,
    val enemies: List<HeroBelief>,
    val objectives: List<ObjectiveState>,
    val lanes: Map<Lane, LaneState>,
    val globalConfidence: Float,
    val staleFields: Set<StateField>,
)
```

`HeroBelief` 使用区域概率分布表达敌方可能位置，而不是伪造精确坐标。概率之外必须记录最后可见时间和推断依据。

## 7. 决策架构

### 7.1 规则处理流程

决策器分为五个阶段：

1. `SafetyGate`：检查死亡、回城、状态过期、布局未知等硬约束。
2. `CandidateGenerator`：基于资源、线路、支援和防守规则生成候选行动。
3. `CandidateScorer`：按价值、可达性、信息质量、风险和时间窗口打分。
4. `ConflictResolver`：应用互斥规则和优先级，选出主建议及备选建议。
5. `DecisionStabilizer`：通过迟滞、最短展示时间和冷却避免建议频繁跳变。

资源 > 推塔 > 打团 > 视野是基础权重，不是无条件覆盖安全约束的硬编码顺序。

### 7.2 规则表达

MVP 使用 Kotlin 中实现的可组合规则接口，不引入外部规则引擎：

```kotlin
interface TacticalRule {
    val id: String
    val version: Int
    fun evaluate(state: GameState): RuleEvaluation
}
```

规则返回是否命中、候选行动、分数分解、证据字段和拒绝原因，便于测试和解释。阈值、权重和冷却时间可放入经过 schema 校验的版本化配置；任意“热更新”文件必须签名验证，并支持原子回滚到内置版本。

### 7.3 决策输出

```kotlin
data class TacticalDecision(
    val schemaVersion: Int,
    val decisionId: String,
    val createdAtElapsedMs: Long,
    val action: TacticalAction,
    val target: MapRegion,
    val reasonCode: ReasonCode,
    val evidence: List<Evidence>,
    val confidence: Float,
    val risk: RiskLevel,
    val validUntilElapsedMs: Long,
    val ruleSetVersion: String,
    val modelVersions: Map<String, String>,
)
```

- `confidence` 范围为 `[0, 1]`，低于展示阈值时不输出方向性强的建议。
- `validUntilElapsedMs` 到期后 UI 必须撤回建议，不能继续展示过时决策。
- `reasonCode` 使用稳定枚举，文案由生成层本地化，不在规则中拼接自然语言。

## 8. 建议生成与展示

`RecommendationComposer` 使用模板生成不超过约 30 字的简体中文建议，例如“敌方打野露上，去蓝区反野，注意中路”。第一版不使用生成式模型，以保证延迟、稳定性和内容可控。

展示层包含：

- `OverlayController`：通过 `WindowManager` 展示非交互或低干扰悬浮卡片。
- `RecommendationRateLimiter`：控制相同建议去重、最短展示时间和更新频率。
- `TextToSpeechController`：可选语音播报，仅播报高优先级且稳定的建议。
- `FallbackNotifier`：悬浮权限不可用时降级到应用内界面或合规通知。

不得遮挡关键操作区域；提供位置、透明度、字号和语音开关。停止分析后立即撤销悬浮层。

## 9. 数据、反馈与隐私

默认策略是“不保存原始帧”：

- 常规运行仅保留内存中的最新帧和短时状态窗口，用后立即释放。
- 性能指标、错误码、模型版本和匿名决策记录可保存在本地环形日志中。
- 保存误判帧、短视频或导出标注样本必须单独征得用户同意，并提供预览和删除入口。
- 导出前裁剪无关区域并移除账号、聊天、通知等潜在个人信息。
- 样本、标注和模型权重不直接提交 Git；小型合法固定样例除外。大型资产使用外部对象存储和带哈希的数据版本清单。

标注 schema 至少包含需求规定的 `timestamp`、`phase`、`state`、`action`、`next_action`、`target_location`、`enemy_positions`，并附加 `schema_version`、素材来源、许可和标注者一致性信息。

## 10. 性能预算与降级

以 2 秒常规目标定义单次处理预算，后续用真机基准修订：

| 阶段 | 常规预算 | P95 上限 | 超限处理 |
| --- | ---: | ---: | --- |
| 获取最新帧与 ROI 预处理 | 80 ms | 150 ms | 降低输入尺寸、复用缓冲区 |
| 小地图与关键状态识别 | 500 ms | 1200 ms | 降频、关闭低优先级识别器 |
| OCR/图标识别 | 250 ms | 600 ms | 降低调用频率、沿用未过期状态 |
| 时序融合与决策 | 80 ms | 200 ms | 记录慢规则并跳过非关键候选 |
| 文案与悬浮展示 | 50 ms | 100 ms | 使用缓存模板 |
| 调度余量 | 1040 ms | 2750 ms | 防止设备差异造成超限 |
| 总计 | 2000 ms | 5000 ms | 进入降级或暂停建议 |

降级顺序：

1. 降低采样频率，始终保留最新帧。
2. 降低输入分辨率或减少非关键 ROI。
3. 降低 OCR、主视野识别等低优先级任务频率。
4. 切换至轻量模型或 CPU 稳定路径。
5. 当布局未知、状态过期或持续超时，暂停战术建议并明确提示“信息不足”。

应持续记录各阶段 P50/P95、帧丢弃率、模型错误率、内存峰值和热状态，但不得记录原始画面内容。

## 11. 测试策略

### 11.1 Android

- `capture`：测试授权状态机、方向变化、资源释放、最新帧策略和服务重启。
- `perception`：使用固定 ROI 样例做预处理、坐标映射和后处理 golden test。
- `reconstruction`：用确定的观测序列测试状态衰减、敌方位置概率和过期字段。
- `decision`：表驱动测试每条规则、冲突处理、置信度、风险和证据链。
- `recommendation`：测试长度、模板、去重、冷却和建议过期撤回。
- 真机基准：至少覆盖一台目标中端设备，测量延迟、内存、CPU、温升和 30 分钟续航表现。

### 11.2 Python 与模型

- 数据 schema 和标签一致性测试。
- 固定切分与随机种子下的训练可复现性测试。
- 按地图区域、阵营、分辨率和 UI 版本分层报告 precision、recall、mAP 或任务适用指标。
- 量化前后精度回归测试，以及导出模型在 Android 运行时的输出一致性测试。
- 敌方位置概率需评估校准误差，不能只报告分类准确率。

### 11.3 端到端回放

建立离线 `ReplayFrameSource`，让录制片段复用与实时采集完全相同的识别、重建和决策管线。端到端测试输出决策时间线、证据、延迟和版本信息，便于回归比较。

## 12. 分阶段实施计划

### 阶段 0：技术探针

- 建立最小 Android 工程、前台服务和 MediaProjection 采集。
- 验证横屏、主流分辨率、悬浮权限和 30 分钟稳定性。
- 用假识别器跑通完整管线并测量基础开销。
- 在目标设备验证 LiteRT 模型的延迟、内存和 delegate 回退；只有无法满足预算时才启动备选运行时评估并新增 ADR。

验收：可稳定展示带时间戳的假建议；持续采集无明显内存增长；会话能完整停止并释放资源。

### 阶段 1：首个垂直切片

- 支持一个明确的游戏 UI 版本和有限分辨率集合。
- 实现小地图裁剪、游戏时间识别和少量关键图标检测。
- 建立 `GameState`、3～5 条打野规则、模板文案和悬浮展示。
- 使用回放片段建立自动化端到端回归。

验收：在选定场景中稳定输出“动作 + 位置 + 理由”，P95 小于 5 秒。

### 阶段 2：端侧视觉模型

- 建立小地图检测数据集、训练和导出流水线。
- 增加英雄、塔、资源检测以及敌方最后可见状态。
- 完成模型清单、校准、版本兼容和降级逻辑。

验收：模型指标达到单独定义的基线，量化后回归可控，中端设备性能达标。

### 阶段 3：时序预测与规则扩展

- 加入敌方区域概率、路线趋势、资源刷新窗口和线路状态。
- 扩展规则集并引入冲突消解、迟滞和置信度校准。
- 建立用户授权的误判反馈闭环。

验收：离线回放中的建议稳定性、命中率和风险误报优于阶段 2 基线。

### 阶段 4：产品化

- 完善设备兼容、权限引导、隐私控制、崩溃恢复和性能监控。
- 评估签名规则包或模型更新；更新失败必须原子回滚。
- 扩展语音、赛后复盘等非核心能力。

## 13. 暂不实施

MVP 阶段明确不做：

- 自动触控、按键注入、读写游戏内存、规避检测等能力。
- 云端实时视频上传与云端主推理链路。
- 单模型端到端直接生成自然语言战术建议。
- 强化学习在线探索或在用户对局中自动更新模型。
- 未经签名和兼容校验的规则、模型热更新。
- 为尚不存在的扩展需求提前拆分多进程或微服务。

## 14. 待验证的架构决策

以下事项必须通过原型或数据后写入 `docs/adr/`：

1. 首批支持的设备、Android 版本、分辨率和游戏 UI 版本。
2. 每种状态字段的新鲜度阈值与建议置信度阈值。
3. 是否需要 Room；MVP 可先使用文件化配置和内存状态。
4. 规则/模型更新是随应用发布，还是使用签名包独立更新。
